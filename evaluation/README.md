# 평가 운영 지침

평가의 목적은 문장이 그럴듯한지 확인하는 데 그치지 않고, 현업이 같은 업무를 정확히 끝낼 수 있는지와 수정 부담이 줄었는지를 확인하는 것입니다.

현재 공개 예시는 합성·미실행 자료입니다. 이 저장소가 실제 현업 인터뷰나 모델 성능 검증을 완료했다는 의미가 아닙니다. 실행 기록이 없으면 결과를 추정해 채우지 않습니다.

## 1. 출력 유형과 평가 단위를 먼저 고정합니다

아래는 현재 등록된 두 업무군입니다. 집계 도구가 허용하는 출력 유형은 [업무군 등록부](../workflows/registry.json)에서 읽습니다. 다른 분야는 [새 업무군 등록 절차](../CONTRIBUTING.md)를 거쳐 유형·완료 조건을 등록한 뒤 집계합니다. 제안 단계의 분야를 기존 유형에 억지로 맞추지 않습니다.

| 유형 | 결과 | 수용 기준에서 확인할 내용 |
|---|---|---|
| N1 | 개인·모바일 노트 | 빠른 재확인에 필요한 사건·결정·미결·후속 행동, 합의한 저장 조건 |
| N2 | 팀 공유 회의록 | 불참자가 이해할 맥락, 결정 상태, 담당자·기한, 검토·공유 범위 |
| B1 | 기업·제품 사실 리포트 | 대상 법인·출처·기간·제품·수치의 정확성, 근거의 범위 |
| B2 | 제품 연결·영업 판단 | 고객 사실과 니즈 가설의 구분, 실제 제품 기능·제약, 적합성·다음 질문 |

기본 단위는 하나의 `CASE-`로 식별한 **고유 업무 사례**입니다. 동일 사례의 재시도·반복 호출·문서 재생성은 새 업무 사례가 아닙니다. 각 실행은 별도 `RUN-`으로 기록하되 동일한 `CASE-`에 연결합니다.

현행안과 변경안은 같은 평가 종료 시점을 기준으로 각각 집계합니다. N1·N2·B1·B2처럼 완료 기준이 다른 결과를 단일 통과율로 합치지 않습니다. 검증하지 않은 유형은 미검증으로 표시합니다.

## 2. 개발 사례와 최종 보류 사례

1. 절차를 개선하기 전에 사례를 나누고 분할 기준과 시점을 기록합니다.
2. 같은 회의·고객·영업 건·원문에서 파생한 자료는 같은 쪽에 둡니다.
3. 개발 사례는 프롬프트·규칙·순서·문서 개선에 사용할 수 있습니다.
4. 보류 사례의 입력·기대 결과·기존 결과는 최종 평가까지 별도로 관리하고 개선에 사용하지 않습니다.
5. 보류 결과를 보고 수정하면 해당 사례는 개발용으로 전환합니다. 새 보류 사례가 없으면 같은 결과를 새로운 독립 검증으로 보고하지 않습니다.

관찰에 사용하거나 수정 이유를 이미 학습한 사례는 개발용입니다. 인력 분리가 어려운 경우 그 한계를 기록하고 새로운 사례로 재확인합니다. 합성 예시는 `example_only`로 관리하며 실제 품질의 성과 분모에 포함하지 않습니다.

공개 승인을 받은 자료라도 최종 보류 사례의 입력·기대 결과·기존 결과는 평가 전에 공개 저장소에 올리지 않습니다. 평가 후 공개했다면 이후의 새로운 개선 주기에서는 독립된 보류 사례로 재사용하지 않습니다. 공개 예시와 개발 자료는 새 보류 사례를 대신하지 않습니다.

## 3. 기대 결과와 검토자

정답 묶음은 한 문장을 그대로 재현하도록 만들지 않습니다. [사례 카드](../templates/case.md)에 다음을 기록합니다.

- 반드시 포함할 사실·결정·조건과 그 근거 위치
- 각 항목의 상태: 제안·요청·수락·확정·미정 등
- 허용되는 표현 차이와 명시해야 할 불확실성
- 원문에서 확인되지 않아 확정하면 안 되는 정보
- 필수 결과·후속 행동과 완료 확인 조건
- 치명 오류, 정상·경계·실패 사례의 수용 조건

현업이 기준을 검토하고 중요한 의견 차이는 평가 전에 조정합니다. LLM 판정은 검토 보조로 사용할 수 있지만 유일한 정답 작성자나 최종 합격 판정자로 사용하지 않습니다. `gold_status=draft`인 사례는 승인된 정답처럼 취급하지 않습니다.

명시된 요청·지시의 수행 대상과 요청 기한은 보존합니다. 상대방의 수락이 없다는 이유로 해당 정보를 삭제하지 않습니다. 요청의 존재, 수락 여부, 확정 상태를 나누고 근거가 없을 때만 미지정으로 둡니다.

## 4. 비교 조건과 실행 기록

[실행 기록](../templates/evaluation-run.md)에 다음 조건을 고정하거나 변경 사실을 적습니다.

| 조건 | 기록 내용 |
|---|---|
| 입력·근거 | 원문·청크·자료 스냅샷과 기준시각, 제공 범위 |
| 절차·규칙 | SOP·PRD·프롬프트·계약의 버전 |
| 수행 환경 | 모델·설정·도구·실행 코드 버전, 권한 범위 |
| 변경점 | 규칙·순서 등 1~2개 개입과 예상 원인 |
| 완료 조건 | 출력 유형, 검토·저장·인계 범위, 평가 종료 시점 |
| 검토 방법 | 검토자, 결과 제시 순서, 수용 기준, 시간 측정 방법 |

가능한 범위에서 검토자가 현행/변경 표시를 보지 않도록 하고 제시 순서를 바꿉니다. 입력·근거·모델을 한꺼번에 바꾸면 어떤 변경이 영향을 주었는지 분리하기 어렵습니다. 필요한 경우 단계별 비교로 나눕니다.

반복 실행은 변동성 확인용으로 별도 기록합니다. 가장 좋은 실행만 골라 대표 결과로 삼지 않습니다. 첫 실행의 품질과 재시도를 포함한 업무 완료를 구분합니다. 수동 재현 결과를 자동 시스템의 실측 개선으로 보고하지 않습니다.

## 5. 지표와 분모

| 지표 | 정의 | 주의점 |
|---|---|---|
| 근거 충족률 | 근거가 의미까지 지지한 사실 주장 수 / 출력의 검증 대상 사실 주장 수 | 평가자가 사실 주장을 분류하며 근거 없는 주장도 분모에 포함합니다. 가설은 별도로 검토합니다. |
| 필수 항목 재현율 | 올바르게 포함된 필수 사실·결정·조건 수 / 기대 결과의 필수 항목 수 | 중복 표현으로 분자를 늘리지 않습니다. 중요한 누락을 별도로 표시합니다. |
| 잘못된 확정 | 제안·미정·가설을 확정으로 바꾼 건수 | 문장 유창성이나 평균 점수로 상쇄하지 않습니다. |
| 사람의 부담 | 초안 검토 시간, 실제 수정 시간, 재작업 횟수 | 능동 작업과 대기를 분리합니다. 준비·추가 확인에 든 사람 시간도 숨기지 않습니다. |
| 업무 완료율 | 합의한 완료 조건에 도달한 고유 업무 사례 수 / 접수한 고유 업무 사례 수 | 재시도를 분모에 추가하지 않습니다. 보류·실패·대기를 각각 기록합니다. |
| 경과 시간·자원 | 시작부터 합의한 종료까지의 시간, 단계별 대기, LLM·검색·도구 호출, 재시도 | 모델 응답 시간만으로 업무 완료 시간을 설명하지 않습니다. |
| 완료당 변동비 | 동일 평가 묶음의 모든 시도 변동비 합계 / 완료한 고유 업무 사례 수 | 실패·재실행 비용도 포함합니다. 같은 사례를 중복 완료로 세지 않습니다. |

분모가 0이면 `N/A`와 이유를 표시합니다. 0/0을 0%나 100%로 바꾸지 않습니다. 미실행·미측정은 빈 측정값 또는 `N/A — 미실행/미측정`으로 표시하고 실제 관측값 0과 구분합니다.

주장의 분할 단위와 필수 항목 목록은 결과를 보기 전에 정합니다. 결과 문장을 잘게 쪼개거나 같은 사실을 반복해 비율을 높이지 않습니다. 자료 부족으로 정당하게 보류한 결과는 상세 보고서 성공과 같은 기준으로 합산하지 않습니다.

비용에는 실제 모델 단가와 입력·캐시·출력 토큰, 검색·도구 비용을 적용합니다. 사용 단가의 시점을 남깁니다. 인프라와 사람 시간은 별도 항목으로 표시하고 중복 계산하지 않습니다. 단가나 사용량이 없으면 비용을 추정 실측값처럼 채우지 않습니다.

## 6. 치명 오류와 채택 순서

다음은 현업과 합의할 치명 오류 후보입니다.

- 원문에 없는 중요한 결정·약속·가격·제품 기능·기한을 확정합니다.
- 사람·기업·계정·제품을 잘못 연결하여 다른 대상의 정보를 사용하거나 반영합니다.
- 없는 출처를 만들거나 핵심 주장을 지지하지 않는 출처를 근거로 제시합니다.
- 합의한 범위·권한을 넘어 상태 변경이나 외부 조치를 실행합니다.
- 실패·반려를 완료로 표시하거나 중복 실행으로 업무 상태를 훼손합니다.

합의한 치명 오류가 발견되면 해당 자동 처리 범위의 채택을 보류하고 원인을 확인합니다. 표본에서 0건을 관측해도 전체 운영의 무오류를 증명하지는 않습니다.

판단 순서는 **치명 오류 → 필수 완료 조건 → 근거·내용 품질 → 사람의 수정 부담 → 시간·호출·비용**입니다. 구체 임계값은 기준선을 확인한 뒤 변경안의 결과를 보기 전에 합의합니다. 호출 수 감소만으로 품질 악화를 채택하지 않습니다.

## 7. 결과 보고와 개정

- 출력 유형별 총 `n`건 중 수용·보류·실패 건수를 보고합니다.
- 개선·동일·악화 사례 수와 사례별 수정 시간 차이를 함께 보여 줍니다.
- 실측값, 추정값, 미측정값을 구분합니다.
- 소표본에서는 개별값·중앙값·범위와 사례 조건을 우선 제시합니다. 높은 통과율이나 극단 분위수를 서비스 보장으로 사용하지 않습니다.
- 실제 사례와 합성 사례를 분리합니다. 실제 사례를 가공해 판단 조건이 달라졌다면 원본과 같은 평가로 합치지 않습니다.
- [결정 카드](../templates/decision.md)에 적용 범위·한계·다음 검증을 남기고 SOP·PRD·Map의 관련 ID를 함께 개정합니다.

공개 저장소에는 승인된 기록과 가공 결과만 보관합니다. 비공개 원문·정답·운영 로그는 별도 보관하고 공개 기록에는 접근 정보를 담지 않은 식별자를 사용합니다.

## 실행용 CSV와 집계

Python 3.10 이상에서 `python3 scripts/summarize_evaluation.py`를 실행합니다. 표준 라이브러리만 사용하며 외부 API는 호출하지 않습니다. 기본 CSV는 헤더만 있고 실측값은 없습니다.

- cases.csv: case_id, source_type(real/synthetic), output_type(업무군 등록부의 유형, 현재 N1/N2/B1/B2), split(development/holdout/example_only), reference. 공개 원문 대신 승인된 가공 사례 참조를 기록합니다.
- runs.csv: evaluation_round, case_id, variant(baseline/proposed), output_type, status(completed/held/failed/pending), attempts, supported_claims, total_claims, required_correct, required_total, review_seconds, edit_seconds, elapsed_seconds, cost, currency.
- 한 행은 평가 회차 × 고유 사례 × 조건입니다. 동일 키의 중복은 오류입니다. 재시도는 새 행을 만들지 않고 attempts와 시간·비용에 누적합니다.
- 접수한 모든 사례를 pending 행부터 등록합니다. 도구는 CSV 밖의 누락 사례를 알 수 없으므로 평가 담당자가 모집단·분모와 대조합니다.
- 숫자 빈칸은 미측정입니다. 0과 다릅니다. 지원 주장/전체 주장과 필수 항목 정답/전체는 쌍으로 입력합니다. 근거 없는 사실 주장도 전체 주장에 포함합니다.
- 회차·출력유형·현행/제안·개발/보류·실제/합성을 분리합니다. example_only는 항상 제외하고 synthetic은 기본 제외합니다. 합성 집계는 --include-synthetic으로 명시합니다.
- 비율의 분모가 0이면 N/A입니다. 부분 측정은 측정 건수를 함께 표시합니다. 시간 평균은 측정된 사례만의 값입니다.
- 완료당 비용은 같은 집계 묶음의 모든 시도 비용 / 완료한 고유 사례 수입니다. 비용 누락·통화 혼합·완료 0이면 관련 값은 N/A입니다.

```bash
python3 scripts/check_repository.py
python3 scripts/summarize_evaluation.py
python3 scripts/summarize_evaluation.py --cases evaluation/cases.csv --runs evaluation/runs.csv
```

구조 검사 통과는 현업 품질·의미 정확성·공개 권한 검증을 뜻하지 않습니다.
