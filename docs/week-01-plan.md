# 첫 주 실행 계획

이 계획은 **5업무일 동안 현업의 실제 일을 복원하고 첫 개선 주기를 준비하는 제안**입니다. 현재 사례 수집·인터뷰·평가가 끝난 상태가 아니며, 날짜만으로 품질 향상이나 v1.0 승격을 보장하지 않습니다.

시작일, 현업·제품·평가 담당자, 확보 가능한 자료와 검토 시간을 먼저 채워 주세요. 외부 연락, 운영 데이터 변경, 배포를 이 계획만으로 실행하지 않습니다.

| 준비 항목 | 확정할 내용 |
|---|---|
| 기간 | 시작일 / 1~5일차의 실제 날짜 |
| 담당자 | 현업 작성·조사 / 업무·영업 책임 / 제품 / AX / 앱·IT / 평가 |
| 우선 출력 | `N1` 개인·모바일 노트, `N2` 팀 공유 회의록, `B1` 기업·제품 사실 리포트, `B2` 제품 연결·영업 판단 중 우선 범위 |
| 자료 범위 | 열람 가능한 실제 사례와 공개 가능한 가공 범위 |
| 종료 기준 | 무엇을 합의·측정하면 첫 주를 마쳤다고 볼지 |

## 1일차 — 현재 동작과 실제 업무를 구분합니다

- 코드·문서에서 읽은 동작을 [코드 근거 카드](../templates/code-evidence.md)에 기록합니다. 읽은 버전, 확인 방법, 실행하지 않은 사항을 구분합니다.
- 각 업무의 최근 실제 사례를 현업과 살펴보고, 목적·독자·시작 사건·완료 조건·반려 이유를 묻습니다.
- 실제 수행 순서와 담당자가 설명하는 이상적인 절차를 [관찰 카드](../templates/observation.md)에 나눠 적습니다.
- 사례 확보량과 검토 시간을 기준으로 첫 주의 범위를 줄이거나 확정합니다.

**남길 결과:** 현재 업무 지도 후보, 코드 확인/현업 가설/미확인 목록, 우선 실패 가설, 자료·역할 계획.

**다음 단계 조건:** 두 업무의 시작·종료·핵심 결과와 책임자를 설명할 수 있어야 합니다.

## 2일차 — 사례를 먼저 나누고 개발 사례를 수동 재현합니다

- 최종 보류 사례를 개발 사례와 먼저 분리하고 잠급니다. 같은 회의·고객·원문의 파생 자료가 양쪽에 들어가지 않도록 합니다.
- 평가 담당이 보류 입력·기대 결과·기존 결과를 관리합니다. 절차 개선 담당은 보류 자료를 참고하지 않습니다.
- 개발 사례만 현업이 평소 방법으로 다시 수행하며, 무엇을 읽고 건너뛰고 확인했는지와 수정 이유를 설명합니다.
- [사례 카드](../templates/case.md)에 필수 사실, 근거 위치, 허용 표현, 금지 추론, 정당한 보류 조건을 기록합니다.
- 관찰에 이미 사용하거나 결과를 보며 규칙을 고친 사례는 개발용으로 둡니다.

**남길 결과:** 사례 원장, 분할 기록, 개발 사례의 기대 사실·근거, SOP·Map v0.2 후보.

**다음 단계 조건:** 수용 가능한 결과가 무엇이며 원문이 그것을 어떻게 지지하는지 설명할 수 있어야 합니다.

## 3일차 — 수용 기준과 현행 결과를 고정합니다

- 현업 의견이 다른 중요 사례는 먼저 조정합니다. 단일 정답 문장보다 사실·상태·완료 조건을 합의합니다.
- SOP 단계와 `PRD-N-01` 등의 요구사항을 연결하고 정상·경계·실패 조건을 적습니다.
- 비교할 입력·근거·출력 유형·권한·모델 설정·종료 시점을 정합니다.
- 현행 결과를 [실행 기록](../templates/evaluation-run.md)에 남기고 실제 검토·수정 시간과 오류를 측정합니다.
- 기준선을 보고 목표를 합의하되 변경안의 결과를 본 뒤 합격선을 옮기지 않습니다.

**남길 결과:** 수용 기준 고정본, 현행 기준 측정, 주요 원인 가설 1~2개, [변경안](../templates/change-proposal.md).

**다음 단계 조건:** 치명 오류와 적용 범위, 측정 단위·분모·미측정 처리가 정해져 있어야 합니다.

## 4일차 — 개발 사례에서 제한된 변경을 비교합니다

- 규칙·판단 순서 등 1~2개 변경을 명확히 하고 나머지 조건을 가능한 범위에서 고정합니다.
- 입력·근거까지 바꿨다면 같은 조건의 비교라고 부르지 않고 변경 범위를 기록합니다.
- 결과의 사실·근거·필수 항목과 사람의 검토·수정 시간, 전체 경과 시간, 호출·재시도·비용을 함께 봅니다.
- 수동으로 새 SOP를 적용했다면 그 결과는 절차 검증입니다. 자동 시스템을 재실행하지 않은 상태에서 시스템 성능 향상으로 보고하지 않습니다.
- 반려 대상, 대기 상태, 재개 조건과 책임이 실제로 작동하는지 확인합니다.

**남길 결과:** 개발 사례의 현행/변경 비교, SOP·PRD·Map·R&R v0.3 후보, 채택 후보와 남은 문제.

**다음 단계 조건:** 변경으로 새로운 치명 오류가 생기지 않았으며, 왜 채택 후보인지 실행 근거를 제시할 수 있어야 합니다.

## 5일차 — 잠근 사례로 확인하고 적용 범위를 결정합니다

- 2일차에 잠근 보류 사례를 최종 확인합니다. 보류 정보가 개선에 사용됐다면 새 사례로 교체하거나 평가의 독립성 한계를 명시합니다.
- 가능하면 다른 담당자가 SOP를 따라 같은 사실·판단 상태·완료 조건을 재현하는지 확인합니다.
- 출력 유형별 표본 수와 수용·보류·실패·치명 오류, 사례별 차이를 보고합니다.
- 업무 책임자가 [결정 카드](../templates/decision.md)에 채택·보류·기각과 이유, 적용 범위, 재검토 조건을 기록합니다.
- 합의된 문서만 개정하고 필요한 구현 변경은 별도 작업으로 연결합니다.

**남길 결과:** 최종 검증 기록, 변경 결정, 합의 범위의 v1.0 후보 또는 미확인 항목을 남긴 v0.x, 다음 주 과제.

## 표본 규모는 1일차에 확정합니다

초기 제안은 업무군별 실제 사례 12건, 총 24건입니다. 업무군마다 개발 8건·보류 4건을 시작안으로 둘 수 있습니다. 장문 회의와 분석 보고서의 검토 시간이 크면 범위를 줄이고, 검증하지 못한 출력 유형을 명시합니다. 이 숫자는 통계적 대표성이나 충분한 검증을 보장하지 않습니다.

N1·N2·B1·B2를 모두 검증하려면 각 유형의 실제 사례가 필요합니다. 업무군별 합계만 채웠다고 모든 출력 유형을 확인한 것은 아닙니다. 합성·경계 사례는 실제 사례와 분리하고 실제 성과 분모에 섞지 않습니다.

## 첫 주 종료 점검

- [ ] 코드 확인, SOP 가설, 현업 관찰, 평가 결과를 구분했습니다.
- [ ] 담당자가 목적·필수 결과·완료 조건을 설명할 수 있습니다.
- [ ] 정상·반려·대기·재개 경로와 책임자가 정해졌습니다.
- [ ] 주요 요구사항에 실제 사례와 수용 조건이 연결됐습니다.
- [ ] 개발·보류 분할과 정보 사용 이력이 남아 있습니다.
- [ ] 미실행·미측정 항목을 수치 0이나 성공으로 표시하지 않았습니다.
- [ ] 채택 범위와 남은 한계, 다음 담당자·작업을 결정했습니다.

현업 사례나 검토자가 확보되지 않으면 문서 초안과 질문 목록까지 진행하고 미확인 상태를 유지합니다. 달력 6~7일은 자료 보완·회신·문서 정리에 사용할 수 있지만 주말 작업을 전제하지 않습니다.

평가의 세부 기준은 [평가 운영 지침](../evaluation/README.md)을 따릅니다.
