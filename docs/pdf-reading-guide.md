# PDF 읽기·활용 안내

대상: [업무 표준화 v0.1 PDF](../reports/workflow-standards-v0.1.pdf), 27쪽, 2026-10-30 KST 기준.

이 문서는 PDF의 목적과 읽는 순서, 해석상 경계, 실제 사례로 수정하는 방법을 설명합니다. PDF 작성 뒤의 대화에서 설명한 핵심 판단과 예시를 프로젝트의 지속 운영 방식에 맞춰 옮겼습니다.

## 1. 이 PDF는 어떤 문서입니까?

현업이 좋은 결과를 만드는 순서와 판단 기준을 복원하기 위한 **v0.1 작업본**입니다. 코드에서 현재 동작과 제약을 확인하고, 두 업무의 SOP·PRD·Map of Work를 제안했습니다. 현업 수행 관찰이나 실제 품질 비교를 마친 표준은 아닙니다.

저장소에는 입력 처리, 근거 수집, 의미 분석, 초안 생성과 일부 검증 규칙이 이미 있습니다. 다음에 확인할 것은 현업이 무엇부터 보고 무엇을 고치는지, 어느 근거 때문에 판단을 바꾸는지, 언제 보류하는지, 어떤 상태를 완료로 보는지입니다.

따라서 PDF는 읽고 끝내는 결과물이 아니라 관찰할 질문과 비교할 기준을 제공하는 시작점입니다. 최신 절차는 workflows/의 Markdown으로 개정하고, PDF는 특정 버전의 공유용 스냅샷으로 남깁니다.

## 2. 페이지별 안내

아래 숫자는 PDF 뷰어의 **물리 페이지**입니다. 표지가 1쪽이고, 본문 장번호와 물리 페이지는 1만큼 차이 납니다.

| 페이지 | 내용 | 읽고 할 일 |
|---|---|---|
| 1–4 | 목적, 문서 관계, 저장소 출발점, 품질 정체 진단 | 실제 문제가 입력·판단·근거·실행 중 어디에 있는지 가설을 세웁니다. |
| 5 | 노트·회의록 지도 | 실제 담당자·시스템·대기·반려를 표시합니다. |
| 6–8 | N01–N12 SOP | 실제 수행 순서와 다르거나 빠진 판단을 찾습니다. |
| 9–10 | 노트 PRD 12개 | 요구하는 동작과 현재 구현을 대조합니다. |
| 11 | 기업·영업 분석 지도 | B1 사실 리포트와 B2 제품 연결의 범위를 구분합니다. |
| 12–15 | B01–B14 SOP | 근거 수집부터 영업 조치까지 판단의 연결을 확인합니다. |
| 16–17 | 분석 PRD 12개 | 사실·가설·제품 기능·완료 상태의 수용 조건을 봅니다. |
| 18 | 출처·주장·제품 연결 기록 | 실제 자료를 어떤 단위로 기록할지 정합니다. |
| 19–20 | 수행 수단과 사람의 R&R | 자동화 수단과 결과 책임자를 구분합니다. |
| 21–22 | 사례 구성·측정 | 기준선, 보류 사례, 평가 분모를 정합니다. |
| 23 | 첫 주 계획 | 자료와 현업 가용성에 맞춰 실행 순서를 조정합니다. |
| 24–25 | 관찰·평가·변경 양식 | 사례 하나를 단계·요구·평가·결정에 연결합니다. |
| 26 | 다음 입력과 미확인 항목 | 첫 노트·기업 사례와 제품 자료를 준비합니다. |
| 27 | 근거와 확인 범위 | 정적 코드 확인과 외부 방법론의 역할을 확인합니다. |

## 3. 확인·제안·검증을 구분해 읽습니다

| 구분 | 의미 | 확대 해석하면 안 되는 것 |
|---|---|---|
| 코드·문서에서 확인 | 열람한 시점의 파일·계약·구현에서 읽은 내용 | 현재 운영에서 실행됐거나 품질을 달성했다는 뜻은 아닙니다. |
| 업무 가설·제안 | 현업이 수행해 보고 수정할 절차·역할·요구 | 이미 승인된 표준이나 현재 제품의 지원 기능은 아닙니다. |
| 현업 관찰 | 실제 사례에서 수행한 순서와 수정 이유 | 한 사례가 모든 팀·고객에 적용되는 규칙은 아닙니다. |
| 평가·채택 | 고정한 조건의 비교와 근거에 따른 결정 | 문서 채택이 구현·배포·운영 검증을 대신하지 않습니다. |

PDF의 SOP·PRD·지도·R&R은 기본적으로 제안입니다. PRD에서 “가능해야 한다”고 적힌 항목이 현재 API에서 지원되는지는 별도 확인합니다. 단계별 재실행, 버전 충돌 처리와 같은 동작은 이 구분이 특히 필요합니다.

## 4. 왜 모델 변경 전에 업무를 봅니까?

느끼는 품질 정체는 서로 다른 원인에서 생길 수 있습니다. 전사 누락, 중요한 기준의 부재, 근거 부족, 실행 상태 오류, 검토자 간 기준 차이, 모델의 의미 오류를 구분해야 합니다.

| 관찰한 문제 | 먼저 비교할 것 |
|---|---|
| 이름·날짜·결정이 틀림 | 사람이 보정한 동일 입력으로도 오류가 나는지 |
| 중요한 내용이 빠짐 | 현업이 필수라고 보는 사실과 출력 기준이 있었는지 |
| 기업 내용은 많지만 영업에 쓸 수 없음 | 고객 문제와 제품 기능을 연결하는 판단·자료가 있는지 |
| 링크는 있지만 결론을 믿기 어려움 | 원문이 해당 주장을 실제로 지지하는지 |
| 결과는 생성됐지만 일이 끝나지 않음 | 검토·저장·등록·인계의 완료 상태가 분리돼 있는지 |

SOP를 작성했다는 이유만으로 품질이 개선되는 것은 아닙니다. 실제 사례에서 어떤 원인이 줄어드는지 비교해야 합니다.

## 5. 노트·회의록은 어떻게 해석합니까?

개인 노트는 빠른 재확인과 다음 행동이 중심입니다. 팀 공유 회의록은 불참자가 결론과 판단 배경, 미결 사항을 이해해야 합니다. 같은 원문이어도 두 결과물의 필수 내용과 분량은 다를 수 있습니다.

N01–N04는 목적·원문·접수·전사 확인, N05–N08은 안건·결정·후속 행동·초안, N09–N12는 검토·수정·반영·피드백입니다.

핵심은 **사실, 요청·제안의 상태, 수락·확정 여부**를 함께 남기는 것입니다. 가상 발언 “김 대리님, 금요일까지 초안을 보내 주세요”에는 요청 대상과 요청 기한이 있습니다. 수락 발화가 없다고 이름·기한을 지우지 않습니다. 수락 여부를 별도로 표시합니다. “금요일까지 검토해 보면 어떨까요?”는 확정 업무와 구분합니다.

마감일과 참석 일정, 초안 생성과 실제 등록도 구분합니다. 분석이 성공했어도 저장·공유·후속 조치가 남아 있을 수 있습니다. 개인 노트의 자기 확인과 팀 회의록의 검토를 같은 승인 절차로 강제하지 않습니다.

## 6. 기업 분석·제품 연결은 어떻게 해석합니까?

B1은 검증한 기업·제품 사실을 전달하는 결과물입니다. B2는 고객의 업무 문제 가설과 자사제품의 기능·제약을 연결해 다음 영업 행동을 정합니다. 기업 소개와 뉴스 요약만 충실하다고 B2가 완성되는 것은 아닙니다.

연결 검토에는 고객 사실, 문제 가설, 제품 기능의 근거, 적용 조건, 부적합·반대 근거 점검, 확인 질문이 필요합니다. 가상의 고객사가 증설 계획을 발표했다면 발표 사실과 실제 착공·완료는 구분합니다. 관리 부담 증가는 가설이고 예산·구매 의사는 확인 대상입니다.

공식 제품 문서는 기능 소개를 뒷받침할 수 있지만 고객 환경에서의 실제 성과까지 자동으로 증명하지 않습니다. 제조사 기능과 판매·구축사의 역할, 현재 기능과 로드맵, 연결·별도 재무와 비교 기간도 구분합니다.

**적합·조건부·부적합·미확인**은 모두 가능한 결과입니다. 반대 근거를 발견하지 못했다면 확인 범위를 기록합니다. 빈칸을 채우기 위해 반대 내용이나 고객 니즈를 만들어 내지 않습니다.

## 7. 역할 분담을 호출 구조로 바로 바꾸지 않습니다

코드·API는 형식·ID·중복·계산·확정 상태를 처리합니다. RPA는 화면으로만 가능한 반복 동작의 후보입니다. ASR·OCR·화자분리는 인식 모델이며 정형 RPA와 다릅니다. LLM은 의미 해석과 작성·가설을 보조합니다. 현업은 목적·중요도·예외·기능 약속·수용 여부를 확인합니다.

SOP의 12단계 또는 14단계는 같은 수의 LLM 호출을 요구하지 않습니다. 단계마다 사람 책임을 적어도 각 단계의 별도 승인창을 뜻하지 않습니다. 의미 분석과 초안 검토는 합의한 지점에서 통합할 수 있습니다. 호출·검토 범위는 품질·지연·비용 비교로 조정합니다.

## 8. 실제 사례로 어떻게 고칩니까?

처음에는 노트 한 건, 기업 분석 한 건, 제품 기능 자료 한 묶음이면 됩니다.

1. 현업이 어떤 자료를 어떤 순서로 확인했는지 기록합니다.
2. 결과의 수정 전후와 수정 이유를 확보합니다.
3. 표현 취향과 사실·판단·절차·실행 오류를 구분합니다.
4. 영향을 받는 N/B 단계와 PRD 요구 ID를 찾습니다.
5. 규칙 하나를 바꾸고 수용 조건과 평가 사례를 함께 수정합니다.
6. 다른 사례에서 같은 규칙이 유효한지 확인합니다.
7. 채택·보류·기각과 적용 범위를 결정 기록으로 남깁니다.

PDF는 PRD 표 안에서 N-01/B-01처럼 짧게 표기합니다. 저장소에서는 PRD-N-01/PRD-B-01로 통일하며 같은 요구를 가리킵니다. [운영 방식과 ID](operating-model.md)

## 9. 첫 주에 무엇을 검증합니까?

첫 주는 현업 관찰, 개발·보류 사례 분리, 수용 기준과 기준선, 수동 절차 비교, 다른 담당자와 보류 사례의 재확인 순서입니다. PDF의 11월 2일–6일 일정은 2026년 최초 계획안이며 참여자의 자료·가용성에 맞춰 조정합니다.

업무군별 12건·총 24건은 초기 표본 제안입니다. 처음부터 모두 준비할 필요는 없고, 검토 시간과 사례 다양성을 보고 확정합니다. 표본 수가 작으므로 서비스 전체의 성능 보장을 주장하지 않습니다.

평가는 근거 충족, 필수 내용 보존, 잘못된 확정, 현업 검토·수정 부담, 고유 업무의 완료, 전체 시간·비용을 봅니다. N1/N2/B1/B2는 구분하고, 분모가 없으면 N/A입니다. 재시도는 별도 업무로 세지 않고 시간·비용에 포함합니다. 보류 정보를 보고 규칙을 바꾸면 해당 사례는 개발용으로 전환합니다.

## 10. 어떻게 기여하면 됩니까?

문서 한 장을 완성하는 대신, 사례와 규칙의 연결을 한 번 개선해 주세요. 직접 수행한 업무의 가공 사례, 놓치기 쉬운 예외, 판단이 갈리는 부분, 검토 시간 기록이 유용합니다.

공개 가능한 자료와 합성 예시는 구분합니다. 실제 고객·회의 원문과 보류 평가 자료는 별도 비공개 환경에서 관리합니다. 공개 저장소에는 기여할 권한이 있는 가공 자료와 검증 가능한 판단을 올립니다.
