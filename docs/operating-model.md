# 지속 운영 방식

이 프로젝트는 여러 분야에서 접수한 사례·관찰·코드 근거를 바탕으로 SOP·Map of Work·PRD·평가 사례를 함께 개정하는 독립적인 작업 공간입니다. 특정 제품의 개발 문서나 공식 연동 목록을 관리하는 곳이 아닙니다. 프로젝트별 출처와 구현 사실은 해당 기여의 공개 범위 안에서 관리합니다.

현재 문서는 **v0.1 제안**입니다. 현업 인터뷰, 실제 사례 평가, 품질·시간·비용 측정을 완료했다는 뜻이 아닙니다. 실행하지 않은 평가에는 결과 수치 대신 `미실행`을 기록합니다.

## 1. 코드에서 확인한 것과 현업의 일을 구분합니다

| 구분 | 말할 수 있는 내용 | 아직 말할 수 없는 내용 |
|---|---|---|
| 코드·문서 확인 | 특정 버전의 함수·계약·분기·검증 규칙을 읽었습니다. | 그 코드가 현재 운영에 배포되어 있거나 현업이 그대로 사용한다고 단정할 수 없습니다. |
| SOP 가설 | 이 입력과 판단, 인계가 업무에 필요할 것으로 제안합니다. | 현업 표준 절차로 합의되었다고 할 수 없습니다. |
| 현업 관찰 | 특정 사례에서 담당자가 실제로 수행한 순서와 판단 이유를 확인했습니다. | 한 사람·한 사례의 행동을 모든 업무에 적용할 수는 없습니다. |
| 사례 평가 | 고정한 조건과 사례에서 결과를 검토하고 측정했습니다. | 소표본 결과를 전체 서비스의 성능 보장으로 확대할 수 없습니다. |
| 채택 결정 | 지정한 책임자가 근거를 보고 특정 적용 범위를 승인했습니다. | 다른 부서·출력 유형·제품 버전에도 자동으로 유효하지는 않습니다. |

근거 상태와 채택 상태는 별도로 기록합니다. 코드를 확인한 요구사항도 현업에서는 보류될 수 있습니다. 현업이 채택한 절차도 아직 시스템에 구현되지 않았을 수 있습니다.

## 2. 한 번의 개선 주기

| 순서 | 수행 내용 | 남길 기록 | 다음 단계 조건 |
|---|---|---|---|
| 1 | 현재 코드·API 계약·문서의 동작과 미확인 부분을 읽습니다. | `CODE-` 근거 카드 | 확인 방법·버전·범위가 구분됩니다. |
| 2 | 목적, 입력, 판단, 결과, 예외, 인계를 가설로 정리합니다. | SOP·Map of Work 초안 | 현재 구현 설명과 필요한 업무 절차가 구분됩니다. |
| 3 | 관찰 사례를 개발용으로 지정하고, 별도의 최종 보류 사례를 확보·잠근 뒤 현업 수행을 관찰합니다. | `OBS-` 관찰 카드, `CASE-` 사례, 분할 기록 | 실제 행동·이상적인 설명·우회 작업·수정 이유와 보류 관리가 구분됩니다. |
| 4 | 업무 규칙과 수용 기준을 합의합니다. | SOP·PRD·Map·R&R 수정안 | 결과를 무엇으로 수용하거나 반려할지 설명할 수 있습니다. |
| 5 | 평가 조건을 고정하고 보류 사례의 잠금 상태와 정보 사용 이력을 확인합니다. | 사례 분할 기록, 평가 계획 | 보류 자료를 개선에 사용하지 않았으며 비교 조건이 정해졌습니다. |
| 6 | 개발 사례에서 원인 가설을 확인하고 제한된 변경을 비교합니다. | `CHG-` 변경안, `RUN-` 실행 기록 | 조건과 변경점, 결과 및 사람의 수정 부담이 남습니다. |
| 7 | 잠근 보류 사례를 평가하고 현업이 채택·보류·기각을 결정합니다. | `DEC-` 결정 기록 | 적용 범위, 남은 한계, 재검토 조건이 명확합니다. |
| 8 | 같은 ID의 문서를 개정하고 새 문제를 다음 주기로 넘깁니다. | 문서 버전, 변경 이력, 후속 과제 | 근거에서 변경 결정까지 다시 찾아갈 수 있습니다. |

사례 확보와 분할은 개선 전에 이루어져야 합니다. 관찰에 사용한 사례, 결과를 보며 규칙을 고친 사례는 개발용입니다. 최종 보류용 사례는 별도로 확보하고 관리합니다. 보류 사례를 미리 확보하지 못하면 절차 초안 작업은 진행할 수 있지만, 최종 평가에는 개선에 사용하지 않은 새 사례가 필요합니다.

## 3. 실패 원인을 먼저 나눕니다

품질 문제를 곧바로 모델 한계로 분류하지 않습니다.

| 원인 가설 | 확인할 내용 | 분리해서 확인하는 방법 |
|---|---|---|
| 입력 | 전사·화자·첨부·청크·필수 조건의 누락 | 사람이 보정한 같은 입력으로 비교합니다. |
| 업무 절차 | 판단·검토·저장·인계·재개 단계의 누락 | 현업이 수동으로 끝내는 과정을 재현합니다. |
| 규칙 | 중요도·완료·미정·예외 기준의 차이 | 현업이 합의한 기준을 명시합니다. |
| 맥락·근거 | 다른 대상의 정보, 오래된 자료, 근거 없는 주장 | 검증한 동일 근거 묶음을 제공합니다. |
| 실행 | 필드 유실, 날짜·ID 오류, 중복 실행, 잘못된 상태 | 고정 응답으로 정형 처리만 확인합니다. |
| 평가 | 검토자 불일치, 부정확한 정답, 모호한 합격 조건 | 기대 사실과 허용 표현을 먼저 조정합니다. |
| 모델 수행 | 올바른 입력·근거·규칙에서도 반복되는 의미 오류 | 통제한 조건에서 확인하고 필요한 대안만 비교합니다. |

한 실패에 여러 원인이 있을 수 있습니다. `원인 추정`, `분리 확인`, `변경 후 재확인`을 구분합니다. 수동 SOP 재현은 업무 절차의 타당성을 확인하는 활동이며, 실제 시스템을 재실행하지 않았다면 시스템 성능이 개선됐다고 보고하지 않습니다.

## 4. 책임과 수행 수단

최종 책임자는 사람입니다. AI·API·RPA는 수행 수단이며 결과의 책임자가 아닙니다.

| 역할 | 맡을 일 |
|---|---|
| 현업 작성·조사 담당 | 실제 사례, 작업 순서, 판단 이유와 수정본을 제공합니다. |
| 업무·영업 책임자 | 목적·수용 기준·예외·후속 행동과 적용 범위를 결정합니다. |
| 제품 담당 | 현재 기능·제약·버전·도입 조건과 고객에게 약속할 범위를 확인합니다. |
| AX·개선 담당 | 근거와 가설을 구분하고 SOP·PRD·지도·평가·변경 이력을 연결합니다. |
| 앱·IT 담당 | 구현, 계정·권한, 상태, 저장·연계·복구의 동작을 확인합니다. |
| 평가 담당 | 기대 사실·수용 기준을 정리하고 보류 사례와 검토 결과를 관리합니다. |

한 사람이 여러 역할을 맡을 수 있습니다. 다만 보류 사례를 읽으며 절차를 개선한 사람의 동일 사례 평가를 독립된 최종 검증으로 표시해서는 안 됩니다. 인력 분리가 어렵다면 새 사례를 확보하거나 검증 한계를 명시합니다.

역할표의 검토 책임은 매 단계 별도의 승인 요청을 뜻하지 않습니다. 연속된 의미 분석·초안 검토는 합의한 지점에서 묶을 수 있습니다. 추가 확인은 중요한 불확실성·권한·변경·예외에 따라 요청합니다.

### 수행 수단을 고르는 질문

- 규칙과 입력을 명시하면 결과를 재현할 수 있습니까? 정형 코드·API를 우선 검토합니다.
- 비정형 의미 해석이 필요합니까? LLM에 제공할 근거와 결과 검증 방법을 정합니다.
- 안정적인 API가 없고 UI에서만 가능한 반복 업무입니까? 화면 변화와 실행 결과를 확인할 수 있을 때 RPA를 검토합니다.
- 오류의 영향, 권한, 가역성, 검증 가능성, 예외 빈도와 사람 시간 절감 가치가 어떻습니까?
- 사람이 판단해야 하는 가치 충돌이나 업무상 약속이 남아 있습니까? 담당자와 인계 조건을 명시합니다.

SOP 단계 수는 LLM 호출 수가 아닙니다. 한 번에 처리해도 되는 판단과 선행 근거가 필요한 판단을 구분하고, 호출 수는 품질·지연·비용을 확인한 뒤 결정합니다.

## 5. ID와 버전

| 기록 | 예시 ID | 연결 대상 |
|---|---|---|
| 코드 근거 | `CODE-N-001` | 확인한 버전, 단계 `N01`, 요구 `PRD-N-01` |
| 관찰 | `OBS-N-001` | 실제 사례, 단계, 관찰한 판단 |
| SOP 단계 | `N01`, `B01` | PRD, 지도 노드, 예외 경로 |
| 요구사항 | `PRD-N-01`, `PRD-B-01` | SOP 단계, 수용 조건, 평가 사례 |
| 사례 | `CASE-N-001` | 입력·기대 사실·분할·출력 유형 |
| 실행 | `RUN-N-001` | 사례, 현행/변경안, 조건, 결과 |
| 변경안 | `CHG-N-001` | 원인 가설, 영향 범위, 비교 계획 |
| 결정 | `DEC-N-001` | 변경안, 실행 근거, 채택·보류·기각 |

연결 예시는 `CODE-N-001 → N01 → PRD-N-01 → CASE-N-001 → RUN-N-001 → DEC-N-001`입니다. 실제로는 여러 근거·단계·사례가 연결될 수 있으며 일대일 관계를 강제하지 않습니다.

같은 문제를 수정할 때 ID를 새로 만들어 이력을 끊지 않습니다. 문서 버전, 공개 저장소의 커밋, 변경 이유와 이전 결정의 대체 관계를 남깁니다. 원문·기대 결과·조건이 바뀐 실행은 새 `RUN-`으로 기록합니다. 기존 기록의 오류를 고치면 정정 내용과 이유를 남깁니다.

PDF는 특정 버전의 읽기용 스냅샷입니다. 최신 상태는 저장소의 문서·기록·변경 이력에서 확인합니다. PDF의 PRD는 필요한 동작을 설명하며 현재 구현 여부를 보증하지 않습니다.

## 6. 공개 자료와 비공개 원문

이 공개 저장소에는 승인된 설명과 공개 가능한 가공 사례만 넣습니다. 실제 회의 원음·전사, 고객 정보, 내부 제품 문서, 원본 코드, 인증 정보와 비공개 파일 링크는 별도로 관리합니다.

공개 카드에서는 비공개 원문을 `PRIVATE-SRC-001` 같은 식별자로 참조할 수 있습니다. 식별자는 접근 수단이 아니며, 실명·고객명·내부 경로·서비스 주소를 포함하지 않습니다. 권한 있는 검토자는 별도 보관 위치에서 원문과 기대 결과를 확인합니다.

가공할 때는 개인정보뿐 아니라 회사·프로젝트를 알아볼 수 있는 조합, 수치, 일정과 문맥도 확인합니다. 가공으로 판단 조건이 바뀌었다면 원본 평가와 같은 사례라고 취급하지 않습니다. 공개 가능한 요약만으로 재검증할 수 없다면 그 한계를 기록합니다.

합성 예시는 양식과 판단 규칙을 설명하기 위한 자료입니다. 실제 현업 성과, 모델 성능, 제품 기능 검증의 근거로 집계하지 않습니다.

공개 가능 여부와 보류 사례의 독립성은 다른 조건입니다. 최종 보류 입력·기대 결과·기존 결과는 평가 전에 공개하지 않습니다. 공개한 사례를 이후 개선 주기의 새로운 독립 보류 사례로 다시 사용하지 않습니다.

## 7. 개정의 종료 조건

다음 조건이 충족된 범위만 채택합니다.

- 현업이 목적과 완료 조건을 설명할 수 있습니다.
- 단계별 입력·판단·결과·예외·인계와 책임자가 정해져 있습니다.
- 주요 요구사항에 검증 가능한 수용 조건과 사례가 연결되어 있습니다.
- 현재 결과와 변경안의 차이가 근거와 실행 기록으로 남아 있습니다.
- 치명 오류, 미확인 사항, 적용 범위와 재검토 조건을 책임자가 확인했습니다.

날짜가 지났다는 이유로 v1.0으로 올리지 않습니다. 현업 관찰과 평가가 없는 범위는 제안 상태로 남깁니다. 채택한 뒤에도 새 실패·고객 답변·제품 변경이 들어오면 같은 ID 체계로 다음 주기를 시작합니다.
