# 기업·제품 조사와 영업 연결 업무

이 문서 묶음은 기업을 조사하고 주요 제품을 이해한 뒤, 필요한 경우 자사 판매제품과의 연결 가능성을 검토하는 업무를 정의합니다. 목표는 보고서를 생성하는 데서 끝나지 않고, 현업이 근거를 확인하고 다음 행동을 결정할 수 있게 하는 것입니다.

**상태는 v0.1 제안입니다. 현업 관찰·실제 사례 검증·운영 수용을 완료하지 않았습니다.** 문서의 합성 사례는 절차를 설명하기 위한 예시이며, 실제 고객 정보나 제품 성능을 나타내지 않습니다.

## 두 가지 결과물

| 구분 | 목적 | 포함하는 결과 | 완료 경로 |
|---|---|---|---|
| **B1 기업·제품 사실 리포트** | 어떤 기업이며 무엇을 어떻게 제공하는지 이해합니다. | 대상 법인, 사업·제품 설명, 확인된 변화·수치, 출처와 자료의 한계 | B01–B08 → B12 사실 검토 → B14 인계 |
| **B2 자사제품 연결 검토** | 고객에게 무엇을 더 확인하고 어떤 제품을 검토할지 정합니다. | B1의 사실, 니즈 가설, 승인된 제품 기능·제약, 적합성 후보, 확인 질문과 영업 행동 | B01–B08 → B09·B10 → B11 → B12 연결 검토 → B13 → B14 |

B1 요청에 제품 추천이나 영업기회 확정을 자동으로 덧붙이지 않습니다. B2에서도 고객 니즈·구매 의사·예산·도입 시기는 각각의 근거를 확인해야 합니다. 적절한 보류·부적합 판정도 유효한 결과입니다.

## 문서 사용 순서

1. [업무 지도](map-of-work.md)에서 요청 범위, 수행자, 인계·대기·반려 지점을 확인합니다.
2. [SOP](sop.md)의 B01–B14를 실제 사례에 적용하고 빠진 판단과 예외를 기록합니다.
3. [PRD](prd.md)의 PRD-B-01–PRD-B-12에 필요한 도구 동작과 수용 조건을 연결합니다.
4. 다른 담당자가 같은 입력으로 재수행한 결과를 비교하고, 수정 이유와 적용 범위를 남깁니다.

SOP의 단계 수는 모델 호출 수가 아닙니다. 선행 근거가 필요한 판단은 순서를 지키고, 제품 자료 준비처럼 독립적으로 할 수 있는 일은 함께 진행할 수 있습니다. 단계별 책임을 정하되 매 단계에 별도 승인 대기를 추가하지는 않습니다.

## 지켜야 할 판단 구분

| 구분 | 기록하는 방법 |
|---|---|
| 기업 식별 | 법인·그룹·자회사·브랜드·사업부를 구분하고 자료의 실제 주체를 확인합니다. |
| 계획과 실행 | “증설 계획을 발표했습니다”와 “착공했습니다”, “완료했습니다”를 각각의 근거로 기록합니다. |
| 자체 주장과 검증 결과 | 회사가 설명한 기능·효과는 주장 주체를 표시합니다. 독립 검증이 없다면 보편적인 성능으로 확대하지 않습니다. |
| 제조사와 판매사 | 제품 제조사, 판매사, 구축·운영·지원 주체의 역할을 따로 적습니다. |
| 숫자와 해석 | 단위·기간·연결/별도·누적/분기를 맞춘 뒤 코드나 시트로 계산합니다. LLM은 계산 결과의 의미를 설명합니다. |
| 사실과 고객 니즈 | 공개된 변화와 그로부터 추론한 업무 문제를 구분합니다. 실제 고객 확인 여부를 남깁니다. |
| 제품 기능과 영업 약속 | 현재 기능, 로드맵, 표준 제공, 추가 개발, 구축 조건을 구분합니다. |

## 연결 검토의 최소 단위

각 연결 후보는 아래 항목을 함께 갖춥니다.

| 항목 | 확인할 내용 |
|---|---|
| 고객 근거 | 어느 법인의 어떤 사실이며, 언제의 정보인지 확인합니다. |
| 니즈 가설 | 어떤 업무 문제가 있을 수 있는지와 다른 설명·반증 조건을 적습니다. |
| 승인된 제품 기능 | 현재 제공하는 기능의 문서·버전·검토자와 제약을 연결합니다. |
| 적용 조건 | 데이터·연동·환경·권한·구축 범위가 맞는지 확인합니다. |
| 부적합·반대 근거 점검 | 맞지 않는 이유와 대안을 검토합니다. 반대 근거를 발견하지 못했다면 확인한 범위를 적습니다. |
| 확인 질문 | 현재 확인되지 않은 조건을 누가 어떻게 확인할지 정합니다. |
| 영업 행동 | 추가 질문·자료 요청·소개 준비·보류·제외 중 담당자가 다음 행동을 선택합니다. |

**“업종이 같으니 제품이 적합하다”는 결론은 충분하지 않습니다.** 고객 측 근거와 제품 측 근거가 연결돼야 하며, 필수 조건이 맞지 않으면 보류하거나 제외합니다.

## 현재 구현에서 참고한 범위

아래 내용은 **2026-10-30 KST에 확인한 저장소 문서·정적 코드의 범위**입니다. 운영 실행·배포 상태·실측 품질을 검증한 결과가 아닙니다. 이 문서 묶음에 원본 코드나 원본 자료를 포함하지 않았습니다. 연결된 저장소는 접근 권한이 필요할 수 있습니다.

| 대상 | 확인한 내용 | 이 문서에서의 활용과 한계 |
|---|---|---|
| WebSearchAgent의 저장소인 GomCrawl | 검색·API·크롤링 결과의 공통 근거 구조와 기업·뉴스 조회 경로를 확인했습니다. [README](https://github.com/thuygom/GomCrawl/blob/a519ea5935a8f66876105fcf272f4cfb91389905/README.md), [근거 구조](https://github.com/thuygom/GomCrawl/blob/a519ea5935a8f66876105fcf272f4cfb91389905/core/schema.py) | 자료 수집과 출처 기록의 출발점으로 참고합니다. 수집 성공이나 점수만으로 사실의 정확성을 확정하지 않습니다. |
| GomCrawl의 기사 관계가치 분류 | LLM 배치 판단과 실패 시 판정 불가 처리 경로를 확인했습니다. [분류 코드](https://github.com/thuygom/GomCrawl/blob/a519ea5935a8f66876105fcf272f4cfb91389905/core/news_quality.py) | 축하·안부·대화 소재는 접촉 계기 후보입니다. 고객의 구매 니즈를 확인한 결과는 아닙니다. |
| TieRPT | 자료 수집, 분야별 분석, 종합 작성, 인용·수치·기간 검사의 경로를 확인했습니다. | TieRPT의 구현·배포 구분 | 확인한 main 코드에는 adaptive-v3가 있으나 해당 문서는 미배포로 표기합니다. [품질 코드](https://github.com/thuygom/TieRPT/blob/255fb5239baf421fdae49384fade44ae016a2faa/tierpt/quality.py), [v3 문서](https://github.com/thuygom/TieRPT/blob/255fb5239baf421fdae49384fade44ae016a2faa/docs/report-v3.md) | 저장소 구현을 현재 운영 기능으로 단정하지 않습니다. 실제 적용 버전은 사용 환경에서 별도로 확인합니다. |
| 자사제품 연결과 영업 판단 | 이번 열람 범위에서는 승인된 자사제품 기능·제약과 고객 근거를 연결하는 전용 구현을 확인하지 못했습니다. | B09–B13은 현업 검증을 거쳐 확정할 제안입니다. 미확인은 기능 부재를 확정한 뜻이 아닙니다. |

## 첫 검증에서 남길 기록

실제 사례를 사용한다면 자료와 결과는 해당 조직이 정한 보관 위치에서 관리합니다. 이 공개 문서에 실제 고객·개인 정보나 비공개 원문을 옮기지 않습니다.

- 사례의 목적과 B1/B2 구분, 입력·원문 버전, 작성 기준일을 남깁니다.
- 필수 사실·허용 표현·금지할 확정과 판정 이유를 먼저 합의합니다.
- 사람의 작업·대기·수정 시간, 반려 지점, 재개 조건을 기록합니다.
- 발행 가능, 현업 수용, 고객 니즈 확인, 영업기회 확정을 별도 상태로 평가합니다.
- 같은 입력을 다른 담당자가 재수행해도 핵심 사실과 판단 상태를 복원할 수 있는지 확인합니다.

아직 개선율·처리시간·자동화 성공률의 측정 결과는 없습니다. 실제 관찰과 검증 결과가 생기면 사례·규칙·요구사항의 버전을 함께 갱신합니다.
