# 노트·회의록 PRD v0.1

> **상태: 제안 · 현업 미검증**  
> 이 문서는 현업이 일을 마칠 수 있도록 도구가 제공해야 할 동작과 수용 조건을 정리합니다. 구현 완료 목록이나 운영 성능 보고서가 아닙니다. 기여별 근거와 확인 수준은 [README](README.md)에 연결합니다.

## 목표와 범위

개인·모바일 노트에서는 본인이 결과·미결·다음 행동을 빠르게 다시 확인할 수 있어야 합니다. 팀 공유 회의록에서는 참석자와 불참자가 결정의 이유·상태·후속 책임을 이해할 수 있어야 합니다. 두 결과의 분량·검토·공유·완료 조건은 각각 합의합니다.

SOP가 현업의 수행과 판단을 설명한다면, PRD는 그 일을 돕는 시스템의 관찰 가능한 동작을 설명합니다. 요구사항마다 정상·경계·실패 사례를 연결합니다. 같은 문장을 출력하는 것이 아니라, 근거와 핵심 사실·상태·조건을 보존하는지를 평가합니다.

아래 수용 조건은 모두 제안입니다. 현재 구현과 일치하는 부분, 배포 확인이 필요한 부분, 새 구현이 필요한 부분을 현업 검증 후 구분합니다. **SOP의 단계 수와 LLM 호출 수는 다르며, 단계별 책임 표시는 매 단계 승인을 요구하지 않습니다.**

## PRD-N-01

**출력 목적과 유형을 구분합니다.**

사용자가 개인 노트, 팀 회의록, 답장 중 필요한 결과를 선택하거나 이미 합의한 기본값을 확인할 수 있어야 합니다. 선택한 목적에 맞게 내용·형식·검토·완료 기준을 적용합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 같은 원문을 노트와 회의록으로 요청하면 각각 합의한 필수 항목을 충족합니다. 노트는 빠른 재확인, 회의록은 결정 이유·후속 책임의 공유 목적을 충족합니다. |
| 경계 | 결정이 없는 회의나 짧은 연락도 목적에 맞게 미결·연락 내용을 남깁니다. 짧지만 명시적인 업무 요청은 단순 연락으로 누락하지 않습니다. |
| 실패·복구 | 답장 목적을 일반 분석으로 처리했거나 출력 유형을 잘못 적용하면 해당 목적부터 다시 선택할 수 있습니다. 사용하지 않을 다른 산출물을 정상 완료로 표시하지 않습니다. |

**연결:** [N01](sop.md#n01), [N08](sop.md#n08). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-02

**중요한 정보에서 원문으로 돌아갈 수 있습니다.**

결정·핵심 수치·요청 대상·수행자·기한 등 검증 대상 정보에서 해당 원문 위치와 필요한 전후 문맥을 확인할 수 있어야 합니다. 출처가 해당 주장의 의미를 지지하는지도 판단할 수 있어야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 검토자가 핵심 주장의 원문 구간을 열어 사실·조건·주체를 대조할 수 있습니다. 본문·첨부·과거 인용의 출처가 구분됩니다. |
| 경계 | 원문이 불명확하거나 일부 첨부가 누락되면 해당 주장에 미확인 이유를 표시합니다. 알려진 인물 정보만으로 현재 사건이 발생했다고 쓰지 않습니다. |
| 실패·복구 | 근거 위치가 잘못됐거나 문맥이 주장을 지지하지 않으면 해당 항목을 반려하고 올바른 근거를 연결하거나 확정을 철회합니다. 근거 유실을 내용 정확성으로 대체하지 않습니다. |

**연결:** [N02](sop.md#n02), [N04](sop.md#n04), [N05](sop.md#n05), [N09](sop.md#n09). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-03

**논의·제안·요청·합의·확정·미결을 구분합니다.**

결정 상태와 요청의 존재, 상대의 수락 상태를 따로 표현할 수 있어야 합니다. 최신 정정이 있으면 현재 상태와 정정 근거를 확인할 수 있어야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 명시적 합의·확정 근거를 반영하고 필요한 조건을 유지합니다. 명시된 요청·지시는 보존하며 수락·거절·보류 여부를 별도로 표시합니다. |
| 경계 | 제안 뒤에 담당·일정 확인이 남은 사례에서 제안 내용과 미결 사항을 함께 남깁니다. 권유형 표현만으로 지시·합의를 확정하지 않습니다. |
| 실패·복구 | 제안을 확정 약속으로 쓰거나 오래된 결정을 최신 정정보다 우선하면 해당 안건을 반려합니다. 상충 근거를 확인한 뒤 현재 상태를 수정하고 관련 행동·일정도 재검토합니다. |

**연결:** [N06](sop.md#n06), [N09](sop.md#n09), [N10](sop.md#n10). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-04

**인물의 역할과 업무 책임을 구분합니다.**

발화자·요청자·요청 대상·수행자·관련 인물을 별도로 이해할 수 있어야 합니다. 확인되지 않은 실명·ID·수행 책임을 임의로 연결하지 않아야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 요청자와 수행자가 다르고 사용자는 수신자인 사례에서도 각 역할을 보존합니다. 상대방의 이행 확인이 사용자에게 필요한 경우에만 확인 업무를 구분해 제시합니다. |
| 경계 | 동명이인·미확인 화자·참여자 정보 누락에서는 후보나 미지정 상태를 유지합니다. 청크의 화자 번호와 누적 전사의 번호를 같은 실명으로 직접 매핑하지 않습니다. |
| 실패·복구 | 화자 오연결 또는 책임자 오지정이 발견되면 관련 결론·행동·일정의 영향 범위를 보여 주고 수정합니다. 무관한 인물·업무까지 일괄 변경하지 않습니다. |

**연결:** [N02](sop.md#n02), [N04](sop.md#n04), [N06](sop.md#n06), [N07](sop.md#n07). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-05

**행동·마감·참석 일정을 구분합니다.**

독립적으로 완료할 수 있는 행동, 업무 제출 마감, 참석 일정, 일정 조율 업무를 구분해야 합니다. 요청 정보와 수락·합의·확정 상태를 함께 보존해야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 보고서 제출 마감이 참석 일정으로 등록되지 않습니다. 명시된 요청·지시의 대상과 기한은 보존하고, 수락 여부와 잠정·확정 상태를 별도로 표시합니다. |
| 경계 | 근거가 없는 담당자·기한만 미지정으로 남깁니다. 제안된 목표일은 제안 상태로 보존합니다. 상대 날짜는 원문 기준시각·시간대가 충분할 때만 해석하며 불충분하면 원문 표현과 확인 필요를 남깁니다. |
| 실패·복구 | 수락이 없다는 이유로 명시된 요청 기한을 지우거나, 요청 기한을 합의된 약속으로 표시하면 반려합니다. 취소·거절·타인만의 행사를 사용자 일정으로 만들었다면 해당 후보를 철회하거나 수정합니다. |

**연결:** [N07](sop.md#n07). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-06

**기록의 목적에 맞는 핵심을 보존합니다.**

현업이 필수로 정한 사실·결정·미결·후속 행동을 유지하면서 독자에게 맞게 압축해야 합니다. 표현은 여러 답을 허용하며, 주체·상태·조건이 바뀌지 않아야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 노트에서 핵심 결과·미결·다음 행동을 빠르게 찾을 수 있습니다. 회의록에서 불참자가 결정 이유·후속 책임을 설명할 수 있습니다. 같은 내용을 여러 섹션에서 불필요하게 반복하지 않습니다. |
| 경계 | 원문이 길거나 중요한 행동이 많으면 합의한 우선순위와 상세 제공 방식을 적용합니다. 한도 때문에 빠진 중요 항목을 조용히 삭제하지 않고 검토할 수 있게 합니다. |
| 실패·복구 | 숫자·조건·주체를 바꾸어 압축하거나 중요한 미결을 누락하면 해당 결과를 수정합니다. 현재 한도 안에서 필수 내용을 제공할 수 없다면 출력 정책 변경을 요구사항으로 남깁니다. |

**연결:** [N05](sop.md#n05), [N08](sop.md#n08), [N09](sop.md#n09). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-07

**임시 전사와 최종 분석 결과를 구분합니다.**

진행 상태와 사용할 수 있는 산출물의 범위를 사용자와 후속 시스템이 알 수 있어야 합니다. 최종 AI 분석 성공도 현업 검토·저장·공유 완료와 별도로 표시해야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 청크 입력 중에는 전사 임시본임을 표시하고, 최종 입력과 분석 성공이 확인된 뒤 최종 분석 초안으로 전환합니다. |
| 경계 | 중간 청크가 성공했어도 분석이 대기 중이면 회의록 분석 완료로 취급하지 않습니다. 최종 청크의 일부 분석이 실패하면 성공한 산출물과 실패 상태를 함께 표시합니다. |
| 실패·복구 | 최종 입력 누락·순서 오류·실패가 발생하면 사용 가능한 누적 원문을 보존하고 실제 상태를 표시합니다. 실패한 세션을 성공한 최종본으로 저장하지 않습니다. |

**연결:** [N03](sop.md#n03). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-08

**부분 실패와 지원되는 복구를 보여줍니다.**

성공한 원문·산출물, 실패한 단계와 원인, 재시도 가능한 범위, 다음 담당자를 구분해야 합니다. 기존 요청의 결과 조회와 새 분석 시도를 구별해야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 전사는 성공하고 요약만 실패하면 전사와 실패 정보를 보존합니다. 재사용 가능한 범위와 해당 API 계약을 확인한 뒤 재처리합니다. |
| 경계 | 선택적 단계 재실행이 미지원이면 전체 재실행 또는 다른 지원 경로를 명시합니다. 이를 이미 가능한 기능으로 표시하지 않고 추가 구현 요구와 구분합니다. |
| 실패·복구 | 응답 유실·저장 실패·재시도에서 기존 작업과 대상 시스템 결과를 먼저 확인합니다. 중복 생성·중복 발송을 구분하고, 최종 상태를 확인하지 못하면 대기 또는 실패로 남깁니다. |

**연결:** [N03](sop.md#n03), [N11](sop.md#n11). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-09

**기존 기록의 수정 범위를 지킵니다.**

추가 사실과 수정 지시를 구분하고 대상 범위만 갱신해야 합니다. 같은 기록의 식별자와 요청하지 않은 항목을 보존하며, 확정된 업무·일정과의 충돌을 분리해 보여줘야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 요약만 수정하면 무관한 할 일·일정·기존 노트 ID가 유지됩니다. 변경된 부분과 유지된 부분을 비교할 수 있습니다. |
| 경계 | 추가 사실이 확정된 일정과 상충하면 기존 확정 객체를 보호하고 변경 제안을 별도로 확인할 수 있습니다. 새 사실이 있다는 이유만으로 실제 업무 객체를 덮어쓰지 않습니다. |
| 실패·복구 | 기존 결과 조회 실패나 오래된 기준 버전 충돌을 빈 기록으로 처리하지 않습니다. 앱·백엔드가 최신 버전 확인과 충돌·복구를 관리합니다. 원천 데이터에 기존 `replies`가 없으면 기존 내용을 빈 배열로 덮어쓰지 않습니다. |

**연결:** [N10](sop.md#n10). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-10

**추천과 실제 반영을 구분합니다.**

완료 후보·일정 후보·답장 초안과 실제 상태 변경·등록·발송을 구분해야 합니다. 실행은 이미 합의한 업무 범위와 권한에 따라 이루어지며, 선택한 각 조치의 결과를 따로 확인할 수 있어야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 후보와 초안만 생성하면 기존 할 일 상태·일정·발송 상태는 바뀌지 않습니다. 사용자가 선택했거나 이미 합의된 범위의 조치를 실행한 뒤 대상 시스템 결과를 확인합니다. |
| 경계 | 한 기록에서 일부 일정만 등록하거나 답장은 저장만 할 수 있습니다. 관련 없는 후보는 후보 상태로 남습니다. 이미 권한이 정해진 낮은 영향의 실행에 동일한 승인을 반복 요구하지 않습니다. |
| 실패·복구 | 분석 성공 뒤 저장·등록·전송이 실패하면 실행 실패를 따로 표시합니다. 응답 유실 시 대상 기록을 조회하고 중복 여부를 확인한 뒤 재개합니다. |

**연결:** [N07](sop.md#n07), [N11](sop.md#n11). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-11

**업무 완료와 검토 상태를 목적별로 관리합니다.**

개인 노트와 팀 회의록 각각의 완료 조건을 설정하고, 검토·대기·반려·확정·저장·공유 상태를 실제 업무에 필요한 범위로 보여줘야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 개인 노트는 합의한 자기 확인·저장 조건으로 완료를 판정합니다. 팀 회의록은 합의한 검토·확정·저장 조건과 필요한 공유 결과로 완료를 판정합니다. |
| 경계 | 같은 사람이 작성·검토·확정할 수 있습니다. 현업에 없는 별도 승인자를 강제하지 않습니다. 미결 사항을 정확히 기록한 회의록은 미결이 있다는 이유만으로 무조건 미완료 처리하지 않습니다. |
| 실패·복구 | 확인 대기는 이유·확인 대상·재개 조건을, 반려는 수정할 단계·담당자·사유를 표시합니다. AI 성공이나 HTTP 성공을 업무 전체의 완료로 대신 표시하지 않습니다. |

**연결:** [N01](sop.md#n01), [N09](sop.md#n09), [N10](sop.md#n10), [N11](sop.md#n11). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## PRD-N-12

**개선의 근거를 기록합니다.**

사례별 원문·초안·현업 수정·판정 이유·시간·실행 상태·적용 규칙 버전을 연결해, 무엇을 바꾸었고 왜 채택하거나 보류했는지 설명할 수 있어야 합니다.

| 상황 | 수용 조건의 제안 |
|---|---|
| 정상 | 같은 사례의 현재 결과와 제안 절차 결과를 비교하고 수정 항목·원인·원문 근거·관련 N단계·PRD ID를 남깁니다. 사람의 작업 시간과 대기 시간은 나누어 기록합니다. |
| 경계 | 검토자 의견이 다르면 이견과 조정 이유를 남깁니다. 다른 사례·다른 수행자에게도 기준을 적용하고, 아직 검증하지 않은 범위를 표시합니다. |
| 실패·복구 | 원문·기준·실행 버전이 없어 비교할 수 없으면 평가 불가와 이유를 남깁니다. 실제 사례와 합성 사례를 구분하며 합성 결과를 운영 성과에 포함하지 않습니다. |

**연결:** [N12](sop.md#n12). **검증할 범위:** 위 수용 조건은 제안이며, 기여별 도구의 지원 범위와 현업 사례로 확인합니다. 구현·배포·운영 성능은 별도 근거가 필요합니다.

## 수용 검토에서 함께 볼 질문

- 핵심 문장을 읽은 사람이 무엇이 결정됐고 무엇이 남았는지 설명할 수 있습니까?
- 요청 대상·요청 기한을 보존하면서 수락·합의 여부를 따로 표시했습니까?
- 필수 사실을 압축하면서 주체·조건·숫자·상태를 바꾸지 않았습니까?
- 후속 행동이 독립적인 완료 결과이며 본인과 상대방의 역할이 구분됩니까?
- 원문 근거는 해당 주장의 의미를 실제로 지지합니까?
- 임시·부분 실패·분석 성공·검토·저장·공유 상태를 구분했습니까?
- 초안을 사용할 수 있게 만드는 사람의 수정과 확인 부담이 줄었습니까?

중요한 결정·약속·수치·기한의 창작, 인물 오연결, 근거가 지지하지 않는 확정, 확정 범위를 넘는 실행, 실패를 완료로 표시하는 오류는 사전에 중대한 오류로 합의할 후보입니다. 문장 유창성이나 짧은 생성 시간으로 상쇄하지 않습니다. 실제 허용 기준과 목표값은 현업의 기준선을 확인한 뒤 개선 결과를 보기 전에 정합니다.

## 합성 예시와 단계 추적

다음 예시는 평가 설계를 설명하기 위한 **합성 사례**입니다. 실제 고객 데이터·회의 내용·성과가 아닙니다.

### EV-N-001 — 제안과 미확정 상태

**입력:** “금요일까지 검토해 보면 어떨까요?”라는 제안 뒤에 “담당자를 정한 다음 일정부터 확인하죠”라는 답이 이어집니다.

**기대 결과:** 검토 제안과 제안된 목표 시점을 남기고, 담당자·합의된 일정은 미확정으로 표시합니다. 금요일 완료가 확정됐다고 쓰거나 특정 참석자를 수행자로 지정하면 반려합니다. 기준일이 제공되지 않았다면 실제 달력 날짜도 임의로 만들지 않습니다.

**연결:** N06·N07 → PRD-N-03·PRD-N-05 → EV-N-001 → 실행 결과·판정 이유 → N12 변경 결정.

### 비교 예시 — 명시된 요청을 보존하는 경우

**입력:** “자료 담당자는 2030-04-12 17:00까지 비교표를 보내 주세요.”라고 요청했으며, 수락·거절 여부를 알 수 있는 추가 발언은 없습니다.

**기대 결과:** 요청 대상은 자료 담당자, 요청 기한은 원문에 명시된 시각, 요청 산출물은 비교표로 보존합니다. 수락 여부는 미확인으로 두고 합의된 약속으로 표시하지 않습니다. 시간대가 없으면 시간대까지 임의로 확정하지 않습니다. 수락이 없다는 이유로 요청 대상·기한을 모두 미지정으로 지우는 것도 오류입니다.

**연결:** N06·N07 → PRD-N-03·PRD-N-04·PRD-N-05. 이 비교는 제안의 미확정과 요청 정보의 보존을 함께 검증하기 위한 설명입니다.

## 변경 관리

현업 사례가 들어오면 요구사항 ID를 유지하고 수용 조건·근거·적용 범위·변경 이유를 갱신합니다. 기준을 바꾸었다면 관련 SOP 단계와 평가 사례도 함께 갱신합니다. 실제 사례나 운영 확인이 없는 요구사항은 완료로 표시하지 않으며, 명세 확인·정적 코드 확인·운영 검증의 상태를 각각 남깁니다.

근거 ID는 [README의 근거 목록](README.md#근거)을 참조해 주세요. 비공개 저장소 링크는 접근 권한이 필요할 수 있습니다.
