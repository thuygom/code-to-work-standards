# 노트·회의록 업무 표준화

> **상태: 제안 v0.1 · 현업 미검증**  
> 조사 기준일: 2026-10-30. `IScribe`와 `writingAgent`의 열람 당시 `master` 문서와 정적 코드를 바탕으로 작성했습니다. 실제 현업의 수행 순서, 운영 배포 상태, 출력 품질과 소요 시간은 검증하지 않았습니다.

이 업무의 목적은 원문에서 사건·결정·요청·미결 사항과 후속 행동을 정확히 정리하고, 필요한 사람이 다시 사용할 수 있는 기록을 만드는 것입니다. 현업이 원문을 읽고 판단하고 고치는 방식을 명세한 뒤, 어떤 일을 정형 코드·전문 모델·LLM·사람에게 맡길지 정합니다.

현재 문서는 현업 관찰을 시작하기 위한 작업본입니다. 저장소에 구현이나 지침이 있다는 사실을 현업 절차의 확정 또는 운영 품질의 달성으로 해석하지 않습니다.

## 문서 구성

| 문서 | 답하는 질문 | 식별자 |
|---|---|---|
| [SOP](sop.md) | 무엇을 입력받아 어떤 판단을 하고, 무엇을 남기며, 예외에서 어디로 돌아갑니까? | N01–N12 |
| [PRD](prd.md) | 도구가 어떤 동작과 결과를 제공해야 현업이 일을 마칠 수 있습니까? | PRD-N-01–PRD-N-12 |
| [Map of Work](map-of-work.md) | 누가 무엇을 넘기며 어디에서 검토·대기·반려·재개합니까? | N01–N12 연결 |
| [프로젝트 개요](../../README.md) | 두 업무군을 어떤 방법으로 관찰하고 정립합니까? | 프로젝트 공통 기준 |

단계 ID는 문서·사례·요구사항을 연결하는 기준입니다. **12단계는 12번의 LLM 호출이나 12번의 사람 승인을 뜻하지 않습니다.** 연속된 판단을 함께 처리할 수 있고, 사람 검토도 목적에 맞는 지점에서 통합할 수 있습니다. 구현의 호출 수와 실제 인계 지점은 별도로 확인합니다.

## 업무의 두 분기

| 구분 | 개인·모바일 노트 | 팀 공유 회의록 |
|---|---|---|
| 주된 독자 | 기록을 다시 읽는 본인 | 참석자, 불참자, 후속 업무 수행자 |
| 사용 목적 | 결과·미결·다음 행동을 빠르게 떠올립니다. | 무엇을 왜 결정했고 누가 무엇을 해야 하는지 공유합니다. |
| 필수 내용 후보 | 핵심 결과, 남은 문제, 본인의 후속 행동, 필요한 원문 연결 | 결론, 결정·합의·승인 대기 상태, 요청·행동, 안건 맥락, 리스크·미결, 근거 |
| 검토 경로 제안 | 본인이 중요한 사실과 다음 행동을 확인합니다. | 합의한 작성자·검토자가 의미와 공유 범위를 확인합니다. |
| 완료 조건 제안 | 필요한 내용을 자기 확인하고 대상 기록에 저장했습니다. | 합의한 검토·확정·저장 조건을 충족하고, 공유가 업무 범위라면 그 결과까지 확인했습니다. |
| 현업 확인 사항 | 어떤 내용이 빠지면 다시 쓸 수 없습니까? | 불참자가 추가 설명 없이 결정 이유와 다음 행동을 이해할 수 있습니까? |

한 원문에서 두 결과를 모두 만들 필요는 없습니다. 목적과 독자에 따라 필요한 결과만 선택합니다. 팀 회의록에 별도 결재가 필요한지, 작성자가 바로 공유할 수 있는지는 현업의 현재 권한과 관행으로 정합니다. 개인 노트에 팀 회의록의 검토 절차를 일괄 적용하지 않습니다.

답장 작성은 별도 분기입니다. 답장해야 할 업무 항목인 `replies`, 실제 보낼 문안인 `reply_draft`, 참석 일정인 `schedules`, 업무 완료 확인 후보인 `completion_candidates`의 목적을 구분합니다. 초안이나 후보 생성은 발송·등록·완료 처리를 의미하지 않습니다. [M1, W1, W4]

## 확인 수준을 읽는 방법

| 표기 | 이 문서에서의 의미 |
|---|---|
| 문서 확인 | 저장소의 계약·명세·README에 해당 내용이 있습니다. 실제 운영 동작을 확인했다는 뜻은 아닙니다. |
| 정적 코드 확인 | 열람한 코드나 프롬프트에 해당 분기·상수·보호 규칙이 있습니다. 실행·배포·품질을 검증했다는 뜻은 아닙니다. |
| 제안 | 현업 사례와 함께 조정할 절차·요구사항·역할·수용 기준입니다. |
| 운영 미검증 | 실제 화면, 배포 버전, 시스템 간 연결, 현업 이용 결과를 아직 확인하지 않았습니다. |

SOP·PRD·업무 지도에 별도 표시가 없으면 모두 **제안**입니다. 아래 저장소 사실은 출발점이며, 현업이 합의해야 할 정책과 구분합니다. 근거 링크는 변경 가능한 브랜치를 가리킵니다. 이후 검증에서는 실제 사용한 버전·실행 시점도 기록해야 합니다.

## 현재 저장소에서 확인한 출발점

### 입력 경로와 결과의 의미

| 경로 | 확인한 역할 | 해석할 때의 경계 | 확인 수준·근거 |
|---|---|---|---|
| `analyze_text` | 이메일·메시지·메모를 분석합니다. 일반 분석 외에 짧은 연락 기록과 답장 모드가 있습니다. | 짧다는 이유만으로 중요한 요청을 단순 연락으로 처리하면 안 됩니다. 답장 모드에서는 일반 요약·할 일·완료 후보를 생략하는 계약이 있습니다. | 문서·정적 코드 확인 [W1–W3] |
| `audio_analysis` | 완성된 음성 파일을 전사·화자분리한 뒤 전체 전사를 의미 분석합니다. | 전사 성공과 의미 분석 성공은 다릅니다. 일부 분석 실패는 `partial_error`로 나타날 수 있습니다. | 문서 확인 [M1, M2] |
| `pre_audio_analysis` | 같은 녹음의 청크를 순서대로 받아 전사를 누적하고, 최종 청크에서 의미 분석합니다. | 중간 `success`와 `analysis_pending` 상태를 최종 분석 완료로 표시하지 않습니다. 최종 입력과 분석 성공을 함께 확인합니다. | 문서 확인 [M3] |
| 문서형 회의록 | 노트와 별도 생성 경로가 있습니다. README는 STT 후 별도 회의록 생성 동작을 설명합니다. | 노트와 회의록의 목적·형식·한도를 하나로 합치지 않습니다. 최종 LLM 검토는 코드상 선택 기능이며 기본 활성으로 확인되지 않았습니다. | 문서·정적 코드 확인 [M0, M5] |
| `text_refine` / `audio_refine` | 기존 기록과 추가 사실·수정 지시를 바탕으로 같은 기록의 변경안을 만듭니다. | 원래 노트의 입력 종류가 아니라 이번 수정 입력 방식으로 경로를 고릅니다. 실제 저장·버전 충돌·복구는 앱·백엔드 책임입니다. | 문서·정적 코드 확인 [M0, W3–W5] |

API의 필드명과 상태는 연결을 이해하기 위한 근거입니다. 현업이 사용하는 화면의 상태명, 추가 승인 여부, 실제 저장·공유 절차는 [PRD](prd.md)와 실제 사례로 따로 합의합니다.

### 산출물을 구분해야 하는 이유

| 산출물 | 사용 목적 | 확인한 경계 |
|---|---|---|
| 원문·전사 | 판단 근거를 다시 확인합니다. | 전사 오류·화자 불확실성을 숨기지 않습니다. 화자 번호만으로 실명이나 업무 책임을 확정하지 않습니다. [M3, M6] |
| 모바일 노트 요약 | 결과·미결·다음 행동을 빠르게 다시 읽습니다. | 확인한 두 구현의 요약 본문 한도는 360자이며 할 일·일정은 각각 최대 5개입니다. 이 한도는 현재 구현 사실이며 새 현업 정책의 합의가 아닙니다. [M5, W3] |
| 문서형 회의록 | 판단 이유와 후속 책임을 공유합니다. | 별도 품질 명세는 결론·결정·행동·맥락·리스크·근거를 구분하고 우선 액션 최대 12개를 제시합니다. 프로파일별 형식과 실제 필요량은 별도 확인합니다. [M5, M7, M8] |
| 할 일 | 독립적으로 완료를 확인할 수 있는 결과를 추적합니다. | 요청자·수행자·관련 인물을 구분합니다. 상대방의 일을 본인의 직접 수행 업무로 바꾸지 않습니다. [M6, W2] |
| 일정 후보 | 본인이 참여할 약속을 검토합니다. | 업무 마감일과 참석 일정을 구분합니다. 제안·조율·확정 상태를 보존합니다. [M1, W1, W2] |
| 답장 초안·완료 후보 | 발송하거나 완료 처리할지 판단합니다. | 생성과 실제 실행은 다릅니다. 선택한 후속 조치의 결과를 별도로 확인해야 합니다. [M1, W1] |

## 사람이 책임질 일과 도구가 수행할 일

다음은 배정 원칙의 제안입니다. 최종 책임은 해당 업무를 소유하는 사람에게 두며, AI와 자동화 도구는 수행 수단으로 구분합니다.

| 주체 | 맡길 일 | 사람에게 돌아오는 판단 |
|---|---|---|
| 정형 코드·API | 식별자·형식·순서·상태 확인, 정해진 규칙의 중복 처리, 저장·조회·전송 결과 확인 | 어떤 결과를 확정하고 어디까지 실행할지 정합니다. |
| 전문 ASR·화자분리 모델 | 음성 전사, 발화 구간·화자 특징 추정 | 중요한 이름·숫자·결정 구간과 실제 화자 연결을 확인합니다. |
| LLM | 안건 묶기, 결정 상태 후보, 요약, 후속 행동 후보, 문안·수정안 작성 | 의도·권한·수락·합의·완료 상태와 근거의 적합성을 확인합니다. |
| 기록 작성자·참석자 | 목적·원문·참여자 맥락 제공, 사실 확인, 수정 이유 기록 | 개인 기록의 수용 여부와 필요한 확인 대상을 정합니다. |
| 업무책임자·업무 소유자 | 중요한 결정·확정 상태·변경 권한·공유 범위 판단 | 팀에서 합의할 완료 조건과 예외를 책임집니다. |
| AX 담당 | 관찰 내용, 규칙·예외·평가 기준, 문서 변경 이력 정리 | 현업이 확인하지 않은 가정을 합의된 정책으로 바꾸지 않습니다. |
| 앱·IT 담당 | 실제 저장·버전·연동·복구 관리 | 실행 실패와 내용 판단 실패를 구분해 인계합니다. |

별도 RPA는 안정적인 API가 없고 화면에서만 가능한 반복 작업이 있을 때 검토합니다. 이번 열람 범위에서 브라우저 클릭형 RPA 구현을 확인하지 않았으므로, 기존 정형 코드를 일괄적으로 RPA라고 부르지 않습니다.

## 현업 검증에서 먼저 확정할 사항

1. **사용처와 완료:** 개인 노트와 팀 회의록을 언제 만들며, 어느 상태를 업무 완료로 봅니까?
2. **중요한 정보:** 반드시 남길 결정·미결·행동은 무엇이며, 현재 분량 한도에서 무엇이 누락됩니까?
3. **요청과 수락:** 요청 대상·요청 기한, 상대의 수락·거절·보류를 어떻게 표시합니까?
4. **수정 권한:** 기록의 정정과 이미 확정된 업무·일정의 변경을 누가 구분하고 확정합니까?
5. **인계와 복구:** 어떤 불확실성에서 기다리고, 누가 무엇을 보완하면 어디부터 재개합니까?
6. **검토 부담:** 초안을 쓸 수 있는 결과로 만드는 데 걸린 사람 작업 시간과 대기 시간이 얼마나 됩니까?

현재 한도, 잠정 일정의 허용 범위, 수정된 `replies`의 실제 앱 반영, API별 재시도 범위는 운영 확인 대상입니다. 특히 단계별 부분 재실행이 모든 경로에서 지원된다고 가정하지 않습니다. 세부 경계는 [PRD-N-08](prd.md#prd-n-08)과 [PRD-N-09](prd.md#prd-n-09)에 남깁니다.

공개 문서 안의 예시는 모두 합성 사례입니다. 실제 사례를 사용할 때는 공개 문서에 고객 자료를 붙이는 대신, 권한 있는 보관처에서 사례 ID·단계·요구사항·판정 이유를 연결해 검증합니다. 합성 사례의 결과는 실제 업무 성과나 제품 성능 측정에 포함하지 않습니다.
